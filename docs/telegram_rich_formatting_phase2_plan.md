## 0. Пре-реквизит (человек, ДО запуска Codex)

**Нет блокеров.** Срез 3 НЕ использует `sendRichMessageDraft` (его протокол стриминга
неизвестен и не нужен для псевдо-стрима — см. реш. в разделе 2). Срез 3 строится на уже
понятных примитивах: `sendRichMessage` (есть с фазы 1) + `editMessageText` с параметром
`rich_message` (метод `EditMessageText` уже в коде, добавить поддержку `rich_message:
InputRichMessage` — тип есть с фазы 1). `RichBlockThinking` уже вендорен (раздел 3
референса). Точную форму `editMessageText.rich_message` подтвердить ручным тестом против
живого бота (она ожидаемо = `InputRichMessage`, как у `sendRichMessage`).

---

## 1. Scope фазы 2

1. **Стриминг + Thinking** — эффект «печатается» + блок «Thinking…», ПОД отдельным
   opt-in тумблером (по умолчанию ВЫКЛ). Только режим «бот как AI-инструмент»; в режиме
   «цифровая копия» (имитация человека) стриминг неуместен.
2. **Rich-карточки владельцу** — review-карточки форматируются, владелец видит реальный
   превью ответа.
3. **По-ботовый / по-ролевой тумблер** — гранулярность rich-тумблера (сейчас per-owner).

**Вне скоупа:** структурное дерево `RichBlock` (медиа/карты/LaTeX/details), настоящий
токен-стриминг из LLM (см. реш. по архитектуре ниже) — это фаза 3.

---

## 2. Архитектурное решение по стримингу (обязательно)

**Псевдо-стриминг готового безопасного текста, НЕ сырой токен-стрим.**
- AI-сервис как и раньше отдаёт ГОТОВЫЙ ответ (контракт не меняется, нового
  стриминг-эндпоинта нет).
- `OutputSafetyScanner` + `deanonymize` работают по финальному тексту (как сейчас) —
  безопасность не нарушается, частичные небезопасные куски в чат не утекают.
- Эффект «печатается» создаётся на стороне Go: показать блок `RichBlockThinking`
  («Thinking…»), затем порциями дослать уже безопасный финальный текст через
  `sendRichMessageDraft`, в конце финализировать сообщение.
- Применяется ТОЛЬКО на пути авто-ответа / прямого ответа бота (где нет owner-review).
  В режиме review стримить некуда — там обычная отправка.

## 3. Реализация — 3 СРЕЗА. Один срез за запуск. После каждого: тесты зелёные → СТОП.

### Срез 1 — гранулярность тумблеров (Go + Mini App)
1. **Per-bot/per-role rich-тумблер.** Сейчас `UserSettings.RichFormattingEnabled`
   (per-owner). Добавить scope бота/роли: расширить настройки бота/роли полем
   `rich_formatting_enabled` (найти, где хранятся per-bot/per-role настройки — рядом с
   мультибот-конфигом и `ai_role`). Резолв: эффективное значение = настройка бота/роли,
   иначе наследует owner-уровень. Дефолт — наследование (ВКЛ).
2. **Новый opt-in тумблер «потоковый/AI-режим»** (`streaming_enabled`, по умолчанию
   **ВЫКЛ**) — на том же уровне, что и rich-тумблер (per-bot/per-role + owner).
3. Контракт: если значения нужны AI-сервису — синхронно openapi.yaml + Python + Go;
   если только Go-сторона (как `learning_enabled`) — лишь Go + миграция.
4. Мiniapp: тумблеры в соответствующем экране (бот/роль), дефолты как выше.
5. Миграции (по образцу 106/107). Тесты: резолв эффективного значения; дефолты;
   `streaming_enabled` по умолчанию false. Прогон: `go test ./...`. → СТОП.

### Срез 2 — Rich-карточки владельцу (Go)
1. Найти, где формируются owner-facing review-карточки (там, где сейчас отправляется
   `cardText` владельцу с inline-клавиатурой, `service.go`).
2. Отправлять их через `SendRichMessage` (фаза 1 уже даёт метод), сохранив inline
   `reply_markup`. Превью черновика рендерить как rich (то, что увидит собеседник).
3. Гейт: rich-карточки владельцу включаются тем же эффективным rich-тумблером.
   При выключенном — текущее плоское поведение.
4. Тесты: карточка владельцу уходит rich при ВКЛ; плоская при ВЫКЛ; inline-кнопки
   сохранены. Прогон: `go test ./...`. → СТОП.

### Срез 3 — Псевдо-стриминг + Thinking (Go) — на send+edit, БЕЗ sendRichMessageDraft
1. В `internal/telegram`: расширить существующий `EditMessageText` поддержкой
   `rich_message: InputRichMessage` (тип есть с фазы 1). `RichBlockThinking`
   (`type:"thinking"`) — для плейсхолдера «Thinking…» в rich-сообщении.
2. В `internal/core` на пути авто-ответа/прямого ответа: если `streaming_enabled`
   (эффективный) ВКЛ И `text_format=rich` — последовательность:
   a) отправить плейсхолдер «Thinking…» через `SendRichMessage` → запомнить `message_id`;
   b) когда готов ФИНАЛЬНЫЙ безопасный текст — `editMessageText(rich_message=финал)`
      на этот `message_id` (опц.: 1-2 промежуточных edit для эффекта «печатается»);
   Иначе — поведение фазы 1 (`SendRichMessage`/plain), без плейсхолдера.
3. Текст — ФИНАЛЬНЫЙ (после OutputSafetyScanner/deanonymize). Частичные куски сырого
   ответа НЕ отправлять. Плейсхолдер «Thinking…» не содержит ответа.
4. Идемпотентность: send+edit на один `message_id`; повторная обработка апдейта не должна
   плодить дубли (ключ отправки как в `sendRecipient`). Если edit упал — финальный текст
   всё равно должен уйти (фолбэк: обычный `SendRichMessage`/HTML), сообщение не теряется.
5. `sendRichMessageDraft` (настоящий серверный стриминг) — НЕ реализуем, это фаза 3.
6. Тесты: стрим-путь вызывается только при ВКЛ тумблере и rich; плейсхолдер→edit на тот же
   id; при ВЫКЛ — фаза-1 путь; падение edit → текст доставлен; идемпотентность.
   Прогон: `go test ./...`. → СТОП.

## 4. Безопасность и инварианты (CLAUDE.md)

- Стриминг отдаёт только финальный текст, прошедший `OutputSafetyScanner` и
  `deanonymize` — никаких сырых частичных кусков.
- Privacy-флаги (`no_memory`/`no_training`/`no_summary`/`private`) логику не меняют.
- Идемпотентность отправки сохраняется (стрим-эдиты идемпотентны).
- Стриминг НЕ применяется в режиме «цифровая копия» (имитация человека) — только
  при явно включённом «потоковом/AI-режиме».
- Go: `slog`, без `fmt.Println`; ошибки обработаны или `_` с комментарием.
- Python: type-аннотации; `frozen=True` dataclasses; без bare `except`.

---

## 5. Критерии приёмки

1. rich-тумблер работает по каждому боту/роли; наследует owner-уровень; дефолт ВКЛ.
2. «Потоковый/AI-режим» — отдельный тумблер, по умолчанию ВЫКЛ; включается per-bot/role.
3. При ВКЛ потоковом режиме и rich-ответе собеседник видит «Thinking…», затем текст
   дослается порциями и финализируется; отправляется только безопасный финальный текст.
4. При ВЫКЛ — поведение фазы 1 без регрессий.
5. Rich-карточки владельцу показывают реальный превью (при ВКЛ rich); inline-кнопки целы.
6. Контракт (если затронут) синхронизирован; старые клиенты не ломаются.
7. Все тесты зелёные. Найденные неэффективности/долги — в `docs/backlog.md`.
