## 1. Как работает `sendRichMessageDraft` (из референса — основа реализации)

- Параметры: `chat_id` (**Integer, только приватный чат**), `draft_id` (Integer ≠ 0;
  одинаковый id → анимированное обновление), `rich_message` (InputRichMessage),
  `message_thread_id` (опц.). Возвращает `True` (НЕ Message).
- Черновик **эфемерный, ~30 сек превью**, сам не сохраняется.
- Поток = повторные вызовы с ОДНИМ `draft_id` и растущим `rich_message`.
- **Финализация = существующий `SendRichMessage`** (фаза 1) — он персистит сообщение и
  возвращает реальный `message_id` (и проходит через идемпотентность `MarkSend`).
- **Нет** `business_connection_id`/`reply_*` у draft — ⇒ **draft-стрим применим только к
  собственным приватным чатам бота (bot-transport), НЕ к business-connection.** Для
  business/непереписочных — путь фазы 1/2 без стрима.

---

## 2. Цель и активация

Заменить псевдо-стрим фазы 2 (send+edit) на **нативный draft-стрим**: показать «Thinking…»
плейсхолдером в черновике, затем растущими черновиками «проявить» финальный безопасный
текст, затем **персистнуть финал через `SendRichMessage`**.

**Активируется только если ВСЕ условия выполнены:**
- эффективный `streaming_enabled` = ВКЛ (фаза 2) И `text_format = rich`;
- транспорт = bot (приватный чат, `chat_id` числовой), НЕ business-connection;
- НЕ режим «цифровая копия» (имитация человека).
Иначе — поведение фазы 1/2 без стрима.

**Безопасность (инвариант):** в черновики уходит только ФИНАЛЬНЫЙ текст, прошедший
`OutputSafetyScanner` и `deanonymize`. Сырые/непроверенные фрагменты — никогда.

## 3. Реализация — 1 СРЕЗ (Go-only). Тесты зелёные → СТОП.

1. В `internal/telegram`: метод
   `func (s *BotSender) SendRichMessageDraft(ctx, chatID string, draftID int64, markdown string) error`
   (POST `sendRichMessageDraft`, тело `{chat_id, draft_id, rich_message:{markdown}}`,
   опц. `message_thread_id`; возвращает успех по `ok:true`). `RichBlockThinking`
   передаётся как `<tg-thinking>…</tg-thinking>` прямо в markdown (раздел 3 референса).
2. В `internal/core`, путь авто-ответа/прямого ответа, при активации (раздел 2):
   a) сгенерировать ненулевой `draft_id` детерминированно (напр. из decisionID/чата — чтобы
      ретраи апдейта не плодили новые черновики);
   b) показать «Thinking…» черновик (`SendRichMessageDraft` с `<tg-thinking>`), пока идёт
      обработка (или сразу перед раскрытием, если генерация уже завершена);
   c) когда готов финальный безопасный текст — 1-3 черновика с тем же `draft_id` и растущим
      содержимым (эффект «печатается»); это best-effort, ошибки draft логируем и игнорируем;
   d) **финализировать обязательным `SendRichMessage`** (существующий путь `sendRecipient`/
      идемпотентность). Именно он сохраняет сообщение и даёт `message_id`.
3. Фолбэк: если `SendRichMessageDraft` недоступен/падает — просто пропустить анимацию и
   сразу выполнить `SendRichMessage` (фаза 1). Сообщение никогда не теряется.
4. Идемпотентность: персист = существующий `SendRichMessage` под `MarkSend`-ключом (как
   сейчас); черновики эфемерны и в дедупликации не участвуют; повторная обработка апдейта
   не плодит дублей финала.
5. `editMessageText`/настоящий стриминг — НЕ трогаем. Контракт НЕ меняем.
6. Тесты (см. раздел 4). Прогон: `cd backend-go && go test ./...`. → СТОП.

## 4. Тесты (functional, против контракта)

- draft-стрим вызывается ТОЛЬКО при: `streaming_enabled` ВКЛ + `text_format=rich` +
  приватный bot-чат; иначе — путь фазы 1/2 (стрима нет).
- business-connection отправка НИКОГДА не идёт через draft (нет поля) — фаза 1/2.
- последовательность: Thinking-черновик → растущие черновики (тот же `draft_id`) →
  финальный `SendRichMessage` персистит сообщение.
- `SendRichMessageDraft` падает → анимация пропущена, финал доставлен через `SendRichMessage`.
- идемпотентность: повтор апдейта не создаёт второй финальный send.
- в черновики уходит только финальный (после safety) текст.

---

## 5. Критерии приёмки

1. В приватном bot-чате при ВКЛ `streaming_enabled` + rich собеседник видит нативный
   draft-стрим («Thinking…» → текст проявляется), сообщение затем персистится.
2. Стримятся/персистятся только безопасные финальные данные.
3. Ошибка draft → финал всё равно доставлен; сообщение не теряется.
4. business-connection и режим «цифровая копия» — без стрима, без регрессий.
5. Контракт не затронут. Все тесты зелёные. Долги/неэффективности — в `docs/backlog.md`.
