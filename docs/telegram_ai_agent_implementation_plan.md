# План реализации проекта: AI-агент, который отвечает за пользователя в Telegram

## 1. Назначение документа

Документ описывает пошаговую реализацию рабочего продукта: AI-агента для Telegram, который подключается к аккаунту пользователя, понимает реальные переписки, отвечает от имени пользователя, формирует черновики, автоматически отвечает в разрешенных случаях, ведет память, делает суммаризации за день/неделю/выбранный период и помогает управлять коммуникациями.

Это не обычный чат-бот для общения с пользователем.

Это персональный коммуникационный AI-агент, который работает поверх Telegram-переписок пользователя.

---

## 2. Итоговый продукт

Итоговая система должна уметь:

```text
1. Подключаться к Telegram-аккаунту пользователя через доступный Telegram Business/API-механизм.
2. Получать входящие сообщения из разрешенных чатов.
3. Понимать, кто написал, в каком контексте и с каким намерением.
4. Использовать память о пользователе, собеседнике, отношениях и истории диалога.
5. Генерировать ответы в стиле пользователя.
6. Отправлять ответ автоматически или как черновик на подтверждение.
7. Работать в режимах:
   - silent
   - manual
   - semi-auto
   - auto
8. Суммаризировать переписки за день, неделю или выбранный период.
9. Выделять задачи, договоренности, важные события и риски.
10. Работать с профессиональными ролями:
   - риелтор
   - фрилансер
   - менеджер продаж
   - поддержка
   - рекрутер
   - персональный ассистент
11. Использовать RAG по документам, базе знаний, CRM или другим источникам.
12. Поддерживать тарифы, лимиты, разные модели и privacy-настройки.
13. Вести audit log всех AI-решений и действий.
```

## 3. Главная продуктовая логика

Система должна быть построена вокруг реального сообщения в Telegram.

Формула работы агента:

```text
Входящее сообщение
+ история диалога
+ память о собеседнике
+ стиль пользователя
+ роль
+ RAG-контекст
+ правила приватности
+ оценка риска
= черновик, автоответ, уточнение или игнорирование
```

AI-агент не должен просто “генерировать текст”. Он должен принимать решение, как безопасно и уместно действовать в коммуникации пользователя.

## 4. Основные режимы работы

### 4.1 Silent Mode

AI не отвечает. Он только наблюдает, анализирует и сохраняет контекст.

Функции:

```text
- сохраняет историю;
- делает summary;
- выделяет договоренности;
- выделяет задачи;
- обновляет память;
- готовит дневные/периодические отчеты.
```

### 4.2 Manual Mode

AI генерирует черновик, но не отправляет его без подтверждения.

Функции:

```text
- предложить ответ;
- дать альтернативные варианты;
- объяснить риск;
- позволить пользователю исправить ответ;
- запомнить correction.
```

### 4.3 Semi-Auto Mode

AI отвечает автоматически только при высокой уверенности и низком риске.

Примеры:

```text
- подтверждение встречи;
- стандартный ответ клиенту;
- простое уточнение;
- короткий follow-up;
- low-risk small talk.
```

### 4.4 Auto Mode

AI сам отвечает в разрешенных чатах и сценариях.

Ограничения:

```text
- не обещать деньги, сроки, гарантии без правил;
- не раскрывать приватную информацию;
- не принимать юридически значимые решения;
- не выполнять рискованные действия без подтверждения;
- не отвечать в запрещенных чатах;
- переводить неоднозначные случаи в manual approval.
```

## 7. Ограниченный пул моделей на старте

На старте не нужно поддерживать десятки моделей. Нужен ограниченный пул, который покрывает основные задачи.

### 7.1 Типы моделей

```text
Fast/Cheap Model
- классификация;
- routing;
- простые summary;
- pre-check риска.

Base Generation Model
- обычные ответы;
- черновики;
- стиль пользователя;
- простые роли.

Strong Model
- сложные переговоры;
- конфликт;
- продажи;
- важные клиенты;
- неоднозначный контекст.

Embedding Model
- память;
- RAG;
- поиск по перепискам;
- поиск по документам.
```

### 7.2 Пример стартового пула

```text
Fast/Cheap:
- gpt-4o-mini или аналогичная small-модель

Base:
- gpt-4.1-mini / gpt-4o-mini / Claude Haiku / аналог

Strong:
- gpt-4.1 / gpt-4o / Claude Sonnet / аналог

Embedding:
- text-embedding-3-small или аналог
```

### 7.3 Принцип

В коде нельзя жестко зашивать конкретную модель.

Неправильно:

```python
model = "gpt-4o"
```

Правильно:

```python
model_config = model_router.route(
    task_type="draft_reply",
    tenant_plan="pro",
    risk_level="medium",
    complexity="normal"
)
```


```text
- деньги;
- юридические обещания;
- здоровье;
- персональные данные;
- конфликт;
- агрессия;
- увольнение;
- сделки;
- договоры;
- приватные отношения;
- неоднозначная просьба.
```

### Decision Engine

```text
if chat_mode == disabled:
    ignore

if risk_level in ["high", "critical"]:
    draft

if confidence < threshold:
    draft

if chat_mode == manual:
    draft

if chat_mode == semi_auto and risk_level == "low" and confidence >= threshold:
    auto_reply

if chat_mode == auto and risk_level in ["low", "medium"]:
    auto_reply
```

### Результат

```text
AI автоматически отвечает только там, где это безопасно и разрешено.
```

```text
1. Собеседник пишет low-risk сообщение.

4. Confidence высокий.
5. AI отправляет ответ.
6. Пользователь видит запись в audit log.
```

```text
1. Scheduler запускает daily summary.

3. AI группирует события по чатам.
4. AI выделяет задачи, договоренности, риски.
5. Пользователь получает отчет в Telegram.
```

```text
1. Потенциальный клиент пишет по квартире.
2. AI определяет intent как lead.
3. AI уточняет бюджет, район, сроки.
4. AI использует RAG по объектам.
5. AI предлагает просмотр.
6. AI сохраняет lead context.
```

## 9.5 AI работает в роли фрилансера

```text
1. Клиент пишет с задачей.
2. AI уточняет ТЗ, сроки, бюджет.
```

# 10. Критические архитектурные правила

## 10.1 Нельзя смешивать память пользователей

Каждый запрос должен иметь:

```text
tenant_id
chat_id
request_id
```

## 10.2 Нельзя делать auto reply без policy check

Перед отправкой должны пройти проверки:

```text
chat_mode
risk_level
confidence
privacy_rules
billing_limits
role_policy
```

## 10.3 Нельзя напрямую вызывать конкретную модель из бизнес-логики

Все вызовы идут через:

```text
Model Router → LLM Gateway
```

## 10.4 Нельзя хранить память без возможности удаления

Для всех memory records нужны:

```text
tenant_id
scope
source
created_at
deleted_at
```

## 10.5 Нельзя использовать пользовательские сообщения как системные инструкции

Сообщения собеседников — это untrusted input.

# 11. Главные технические риски

## 11.1 Ошибка в auto reply

Решение:

```text
- risk classifier;
- manual fallback;
- audit log;
- threshold;
- safe mode.
```

## 11.2 Утечка памяти между пользователями

Решение:

```text
- strict tenant isolation;
- tests;
- scoped retrieval;
- query guards.
```

## 11.3 Высокая стоимость AI

Решение:

```text
- model router;
- caching;
- summaries вместо полной истории;
- лимиты;
- cheap models для классификации.
```

## 11.4 Низкое доверие пользователя

Решение:

```text
- manual mode;
- прозрачный audit log;
- privacy controls;
- объяснение решений;
- возможность быстро отключить AI.
```

## 11.5 Некачественная память

Решение:

```text
- memory confidence;
- memory source tracking;
- возможность удалить/исправить память;
- periodic memory cleanup.
```
